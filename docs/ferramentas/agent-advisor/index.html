Como decidimos

Do trabalho a ser feito à plataforma certa

Usamos o Double Diamond para estruturar a jornada (divergir, convergir, divergir, convergir) e o Jobs-to-be-Done para formular cada pergunta pelo trabalho, não pelo nome do produto.

01 · Descobrir

02 · Definir

As pessoas

03 · Desenvolver

04 · Entregar

A decisão

Recomendação, alternativa, placar aberto e um checklist de ação com links oficiais.

Como funciona a pontuação?

Para construir agentes, cinco perguntas valem de 0 a 3 pontos para Agent Builder, Copilot Studio e Microsoft Foundry (máximo 15). Faixas: 12–15 Encaixe forte, 8–11 Bom encaixe, 4–7 Encaixe parcial, 0–3 Não recomendado. Se Copilot Studio e Foundry ficarem a até 2 pontos um do outro, perguntamos quem precisa operar o runtime.

Quais regras eliminam uma plataforma?
  • Usuários externos, app próprio, execução em segundo plano, ações em vários sistemas, Dataverse/APIs ou RAG próprio eliminam o Agent Builder.
  • Orquestração multiagente ou de longa duração elimina o Agent Builder.
  • Runtime sob responsabilidade da engenharia elimina Agent Builder e Copilot Studio: Foundry vence.
E para usar agentes prontos?

Se você quer trabalhar junto, turno a turno, o destino é o Microsoft 365 Copilot (Chat ou agentes integrados). Se quer delegar: alcance fora do M365 (desktop, navegador, arquivos locais) leva ao Microsoft Scout; trabalho dentro do M365, pontual, recorrente ou contínuo, leva ao Copilot Cowork. Indecisão em cadência ou alcance mostra os dois como par complementar.

De onde vêm as regras?

A lógica segue o modelo público do Agent Platform Advisor (versão de jul/2026), adaptada pela NEIVA com o framework Double Diamond + JTBD, caminhos adjacentes (SharePoint agents, Agents Toolkit, GitHub Copilot) e governança com Agent 365. Disponibilidade de recursos em preview/Frontier muda com frequência: confirme no Microsoft Learn antes de decidir.
